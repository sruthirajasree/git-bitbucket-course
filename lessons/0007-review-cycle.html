Lesson 0007 · Phase 2: The Bitbucket daily loop · 12 min

Reviews: respond, update, re-request

You will be able to: handle 'Needs work', approvals, tasks and failing checks without creating a mess.

The PR follows your branch. To change it, push more commits to the same branch. Never open a second PR for review fixes.

git switch feature/PROJ-1234-parse-fix
git pull                       # in case a reviewer pushed a suggestion
# edit
git add -p && git commit -m "PROJ-1234: address review: validate input"
git push

What can block the merge button

BlockerWhat to do
Not enough approvalsAsk reviewers; push fixes; re-request review
Needs work / Request changesFix, push, then clear the status or ask reviewer to re-approve
Open tasksResolve each task (comment checkboxes)
Build failedOpen the build link, reproduce locally, fix, push. Do not merge around it
Conflicts with targetUpdate branch (lesson 11-13)
Branch out of date (if required)Merge or rebase staging into your branch, push
Bitbucket: Settings differ per repo: required approvals, 'reset approvals on new commits', required builds, and which merge strategies are allowed are chosen by repo admins (Data Center: Repository settings -> Merge checks; Cloud: Branch restrictions). Ask your admin; do not guess.

Fixup commits keep review readable

While a PR is in review, push new commits rather than rewriting history. Reviewers can see what changed since they last looked. Squash at merge time if the repo allows it.

Rewriting (rebase/amend + force push) a branch under review hides what you changed since the last review and can make comment threads detached. Prefer new commits until review ends.
