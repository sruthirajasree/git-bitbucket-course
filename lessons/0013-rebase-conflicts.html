Rebase conflicts and force-with-lease

You will be able to: survive a rebase that stops several times, and publish the rewritten branch safely.

Rebase replays your commits one at a time, so it can stop once per commit. The routine is the same as a merge, but you finish with --continue.

git rebase origin/staging
# CONFLICT in app.py while replaying commit 1/2
# fix file ...
git add app.py
git rebase --continue         # NOT git commit
# may stop again for commit 2 ...
# escape hatches:
git rebase --abort            # restore everything
git rebase --skip             # drop the current commit (e.g. became empty)
In a rebase the words are flipped: ours = the branch you rebase onto (staging), theirs = your commit being replayed.

Publishing a rewritten branch

The remote still has your old commit ids, so a plain push is rejected. Use:

git push --force-with-lease

--force-with-lease overwrites the remote branch only if it is still where you last saw it. If a teammate pushed meanwhile, it refuses and protects them. Plain --force does not.

--forceYes, silentlyAlmost never

Bitbucket: Protected branches (staging, release/*) normally forbid history rewrite. Branch permissions can also block force pushes on feature branches if admins choose.
Lost in a rebase? git reflog then git reset --hard ORIG_HEAD (or the sha before the rebase) returns you to the start.

Do it for real

Lab (real git, safe sandbox): conflict-rebase

Stuck? ./labs/lab.sh hint conflict-rebase. The sandbox is a local bare repo that plays Bitbucket, so nothing real is touched. Run from the course folder (~/git-bitbucket-teach) on the machine where Git is installed.
