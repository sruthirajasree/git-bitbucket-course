Lesson 0023 · Phase 5: Hard cases · 14 min

Stacked PRs and dependent branches

You will be able to: split big work into a chain of PRs and rebase the chain after the parent squash-merges.

Big feature? Ship it as a stack: branch B is built on branch A; PR-A targets staging, PR-B targets A. Reviews are small and parallel.

When A is squash-merged, B is orphaned

Staging now has a new commit SQ equal to A1+A2. B's history still contains A1, A2 (different ids): merging B would replay them and conflict. Use rebase --onto to take only B's own commits:

git fetch
git rebase --onto origin/staging <old-A-tip-sha> feature-B
git push --force-with-lease
# retarget PR-B to staging in Bitbucket
Save the old tip sha of A (git rev-parse feature-A) before deleting A. If lost: git reflog.
If you merge A with a merge commit (not squash) instead, B needs nothing special: just merge/rebase staging normally.
Bitbucket: When PR-A merges and its branch is deleted, Bitbucket may retarget PR-B to staging automatically; verify the target and the diff are only B's commits.
