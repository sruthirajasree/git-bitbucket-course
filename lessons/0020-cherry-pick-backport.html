Cherry-pick, hotfixes and backports

You will be able to: copy a fix to another branch and run a hotfix flow without losing it anywhere.

Cherry-pick re-applies one commit's diff on top of your current branch as a new commit.

git switch release/26.2
git cherry-pick -x <sha>          # -x records 'cherry picked from <sha>' in the message
git cherry-pick A^..B             # range
git cherry-pick -m 1 <merge-sha>  # a merge commit
# conflict: fix, git add, git cherry-pick --continue   (or --abort)

Hotfix flow (oldest affected branch first)

1. git switch -c bugfix/PROJ-2000 origin/release/26.2   # branch from the release
2. fix, commit, push, PR -> release/26.2
3. After merge, bring it forward:
   git switch -c bugfix/PROJ-2000-staging origin/staging
   git cherry-pick -x <fix-sha>; push; PR -> staging
Fix the oldest affected line first then forward-port, so no branch regresses. Using -x gives traceability.
Do not cherry-pick between branches that will later be merged into each other without noting it: duplicate commits can cause confusing conflicts. Prefer merging when the branches share lineage.

Lab (real git, safe sandbox): backport

Stuck? ./labs/lab.sh hint backport. The sandbox is a local bare repo that plays Bitbucket, so nothing real is touched. Run from the course folder (~/git-bitbucket-teach) on the machine where Git is installed.
