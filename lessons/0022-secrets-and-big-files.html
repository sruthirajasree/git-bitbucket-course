Secrets and large files

You will be able to: respond to a leaked credential correctly (rotate first) and prevent big-file mistakes.
Rule zero: a secret that was ever pushed is compromised. Deleting it in a new commit does not remove it from history, and others may have fetched it. Rotate or revoke it first, clean up second.
Where is the secret?Do this
Only in working tree (not committed)Add file to .gitignore; do not git add it
Committed locally, not pushedRewrite locally: git reset --soft HEAD~1, unstage the file, recommit. Still rotate if the secret is real
Pushed to a feature branch / PRRotate now. Tell your repo admin / security. Delete the branch/PR; admin may need to garbage-collect
Pushed to shared branch (staging)Rotate now. Incident process. History rewrite (git filter-repo) needs admin coordination + everyone re-clones
# unpushed, secret in the last commit:
git reset --soft HEAD~1
git restore --staged .env
echo ".env" >> .gitignore
git add db.py .gitignore && git commit -m "PROJ-70: add db connect"
# find where a secret entered history:
git log -S"hunter2" --all --oneline

Prevention

  • Keep config in environment variables or a secrets manager, commit an .env.example with fake values.
  • Add .env, *.pem, *.key to .gitignore on day one.
  • Review git diff --staged before every commit.
  • Ask your admin about pre-receive secret-scanning hooks.

Large files

Git stores every version of every file forever, so a 200 MB binary slows every clone. If a push is rejected for size: unpush the commit (reset --soft), remove the file, recommit. For binaries you truly need, use Git LFS (git lfs track '*.bin'), set up before committing them.
