Lesson 0010 · Phase 3: Staying in sync · 14 min

Push rejected and diverged branches

You will be able to: read a rejected push, see the divergence in a graph, and resolve it without force.

The most common error in team work: ! [rejected] ... (fetch first) or non-fast-forward. A teammate pushed to the same branch first. Git refuses to overwrite their work.

Two fixes, both safe

SituationUseWhy
Your own feature branch, only you pushpull --rebaseLinear, no noise
Branch shared with teammateseither; pull --rebase is fine for unpushed local commitsYour local commits aren't shared yet
Many conflicts expectedmergeResolve once instead of per commit
Never answer a rejection with git push --force. It deletes your teammate's commit from the server. If you must overwrite after a rebase of your own work, use --force-with-lease (lesson 13).
Set a default so Git never nags: git config --global pull.rebase true (or false for merge).

Do it for real

Lab (real git, safe sandbox): rejected

Your push is rejected because a teammate pushed first. Publish both commits without force.

./labs/lab.sh start rejected
cd ~/git-sandbox/work     # fix it here
./labs/lab.sh check rejected

Stuck? ./labs/lab.sh hint rejected. The sandbox is a local bare repo that plays Bitbucket, so nothing real is touched. Run from the course folder (~/git-bitbucket-teach) on the machine where Git is installed.

Lab (real git, safe sandbox): stash-pull

Pull is blocked by your uncommitted edits. Update without losing or committing them.

./labs/lab.sh start stash-pull
cd ~/git-sandbox/work     # fix it here
./labs/lab.sh check stash-pull

Stuck? ./labs/lab.sh hint stash-pull. The sandbox is a local bare repo that plays Bitbucket, so nothing real is touched. Run from the course folder (~/git-bitbucket-teach) on the machine where Git is installed.
